# installer — охраняемая установка во внутреннюю eMMC

`h96install.py` пишет образы в eMMC приставки, загруженной с SD-карты в
[rescue-среду](../rescue/README.md). Один файл на Python 3.8+, только
стандартная библиотека.

**Статус: реализовано и проверено только на имитации** (31 тест в `tests/`:
поддельная eMMC с настоящей структурой MPT и DTB-записей, поддельные sysfs и
таблица монтирования). На реальной приставке этот установщик **ещё не
запускался**. Его предшественник с теми же проверками использовался
сопровождающим, но был привязан к одному экземпляру.

## Чем он защищает

- **Личность устройства.** Работает только с eMMC, чей CID вы подтвердили
  вручную при создании профиля; при каждом сеансе CID, размер и таблица
  разделов сверяются заново. Чужое устройство в той же сети — отказ.
- **Разметка.** Таблица разделов (MPT) читается с устройства и обязана
  совпадать с описанием платы в `boards/` до байта, включая контрольную сумму.
  Неизвестная разметка — отказ, а не повод снять проверку.
- **Что не пишется никогда:** bootloader, env, logo, recovery, rsv, tee, crypt,
  misc, сама MPT. В `reserved`, где рядом лежат ключи и калибровка платы,
  разрешена только полезная нагрузка двух DTB-записей.
- **Ни одного непроверенного байта во флеш.** Каждый кусок образа скачивается
  во временную память rescue, сверяется по размеру и SHA-256 и лишь потом
  пишется; после записи весь диапазон читается обратно и сверяется.
- **Бэкап до записи обязателен:** всё, что план изменит, сначала копируется на
  ПК с проверкой хэша на обеих сторонах; `restore` возвращает это обратно.
- **Стирание данных** — только при первой установке и только после ввода
  подтверждения `WIPE-<последние 6 знаков CID>`.
- **Прерванный сеанс** блокирует новые установки, пока вы не продолжите тот же
  план (`--resume`) или явно его не отмените (`journal abandon`).

## Что нужно

- ПК с Linux (на Windows — в WSL; прямой запуск в Windows не проверялся,
  тесты с имитацией приставки там пропускаются), в **одной сети с приставкой**, лучше —
  прямой кабель: rescue открывает root-консоль без пароля. Приставка сама
  забирает файлы с ПК по HTTP и отдаёт бэкап по TCP, поэтому брандмауэр ПК
  должен пропускать входящие соединения на время сеанса. WSL2 подходит только в
  режиме зеркальной сети (mirrored): из NAT-режима приставка до ПК не достучится.
- Выпуск: каталог с образами и `release-manifest.json` (формат ниже).
  **Публичный выпуск сейчас только в исходниках** — образы нужно собрать самим,
  см. [DEVELOPMENT.md](../DEVELOPMENT.md).

## Порядок работы

```bash
I=installer/h96install.py
BOX=192.0.2.202                        # адрес rescue: см. RESCUE.LOG на карте

python3 $I discover --target $BOX      # только чтение: CID, разметка, DTB-записи, монтирование
python3 $I profile-init --target $BOX --board h96proplus-czs32v3 \
        --confirm-cid <CID из discover> --out ~/h96/my-box.profile.json

python3 $I plan --profile ~/h96/my-box.profile.json --manifest release/release-manifest.json \
        --artifacts release/ --first-install --wipe-data --out ~/h96/first.plan.json
# прочитайте план целиком; он печатает свой SHA-256

python3 $I backup --target $BOX --profile ~/h96/my-box.profile.json \
        --plan ~/h96/first.plan.json --out ~/h96/backup-before-first-install
python3 $I install --target $BOX --profile ~/h96/my-box.profile.json \
        --plan ~/h96/first.plan.json --plan-sha256 <SHA плана> \
        --artifacts release/ --backup ~/h96/backup-before-first-install \
        --confirm-wipe WIPE-<последние 6 знаков CID>
python3 $I verify --target $BOX --profile ~/h96/my-box.profile.json --plan ~/h96/first.plan.json
python3 $I rescue-disarm --target $BOX --reboot
```

Обновление — то же без `--first-install` и `--wipe-data`: пишутся только
перечисленные в выпуске части, данные не трогаются.

Откат к содержимому бэкапа:

```bash
python3 $I restore --target $BOX --profile ~/h96/my-box.profile.json \
        --backup ~/h96/backup-before-first-install --confirm RESTORE-<последние 6 знаков CID>
```

Профиль, план, журнал и бэкап **идентифицируют вашу приставку** — не
публикуйте их и не прикладывайте к сообщениям об ошибках.

Полного образа всей eMMC (вместе с boot0/boot1) установщик пока не снимает:
бэкап плана покрывает ровно те байты, которые он меняет. Полная копия перед
первой установкой всё равно желательна.

## Формат выпуска

```json
{
  "release_id": "…",
  "supported_boards": ["h96proplus-czs32v3"],
  "artifacts": [
    {"name": "boot.img",   "target": "boot",   "size": 0, "sha256": "…"},
    {"name": "vendor.img", "target": "vendor", "size": 0, "sha256": "…"},
    {"name": "system.img", "target": "system", "size": 0, "sha256": "…"},
    {"name": "dtb.img",    "target": "dtb",    "size": 0, "sha256": "…"}
  ]
}
```

`target` — имя из раздела `targets` описания платы (`boot` → стоковый `boot`,
`vendor` → стоковый `cache`, `system` → `system`) или `dtb`. Первая установка
требует все четыре.

## Описание платы

`boards/h96proplus-czs32v3.json` — разметка, проверенная на одном экземпляре:
13 записей стоковой MPT и её контрольная сумма совпали с тем, что показано в
файле. Строка `kernel_cmdline_partitions` должна совпадать с `blkdevparts` в
командной строке boot.img — установщик и ядро обязаны видеть одну разметку.
Другая ревизия платы или стоковой прошивки — это новое описание платы после
собственной проверки, а не правка смещений «на глаз».
