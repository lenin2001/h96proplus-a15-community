# Как продолжать разработку

## Статус воспроизводимости

| Часть | Что проверено при публикации | Чего не хватает |
|---|---|---|
| Ядро | ряд из [`kernel/patches/series.json`](kernel/patches/series.json) от чистого Linux v7.1 даёт дерево #112: 30/30 исходных файлов, DTS и `.config` побайтно совпадают; DTB равен установленному (см. [kernel/README.md](kernel/README.md)) | новое ядро на приставке из этого рецепта не загружалось |
| Firmware | `build/fetch-firmware.sh` с закреплённого тега linux-firmware, все SHA-256 совпали | — |
| Rescue и автоскрипт | busybox 1.36.1 собран рецептом со сверкой апплетов; `rescue.img` собирается и при повторной сборке побайтно тот же; файлы карты собираются | публичная версия rescue на железе не запускалась |
| Установщик | 31 тест на имитации eMMC | на железе не запускался |
| AOSP | база — тег `android-15.0.0_r36`; оверлей и активные патчи побайтно дают все локальные изменения дерева сопровождающего, кроме исключённого 0012 ([`aosp-patches/series.json`](aosp-patches/series.json)); полная сборка по этому описанию из свежего клона прошла 15.10.2026 ([подробности](#проверенная-сборка-15102026)) | образы из неё на приставке не загружались |
| Mesa/Panfrost | [`build/build-mesa.sh`](build/build-mesa.sh): NDK r27c, исходники `external/mesa3d` и `external/libdrm` того же тега; в чистой сборке все шесть библиотек попадают в vendor побайтно такими, какими их выдал рецепт | библиотеки из рецепта на приставке не проверялись |
| Образы boot/system/vendor | чистая сборка без пересадки файлов: образы помещаются в разделы, состав и замыкание библиотек vendor проверены | на приставке не загружались; у сопровождающего system/vendor частично собирались «пересадкой» файлов в готовые образы, так что чистая сборка — новая для железа конфигурация |

Перед изменениями прочитайте [STATUS.md](STATUS.md) и [HISTORY.md](HISTORY.md).
Версию Android/API, ревизию AOSP и ядра берите из `series.json` и паспорта
выпуска, а не из имён файлов и комментариев в старых конфигах. В отпечатке
сборки стоит кодовое имя `Baklava` — это эффект конфигурации выпуска
`trunk_staging`, исходники при этом — релизный тег Android 15.

## Карта исходников

- `device/h96proplus/`: продукт, init, fstab, политики, оверлеи, звук, пульт и
  демон мыши `h96mouse` — см. [device/h96proplus/README.md](device/h96proplus/README.md).
- `dt/`: Device Tree платы. DTB на eMMC лежит в двух записях раздела `reserved`,
  а не в boot.img — см. [dt/README.md](dt/README.md).
- `kernel/`: конфигурация, ряд патчей (`patches/series.json`), канонический
  драйвер питания `meson_gx_pm.c`, паспорт Wi-Fi firmware.
- `aosp-overlay/`: файлы, заменяющие файлы AOSP целиком; `external/v4l2_codec2` —
  накопленное рабочее состояние модуля Codec2 (CSD/flush/EOS, MMAP-копия).
  V4L2 OUTPUT принимает сжатый поток, CAPTURE возвращает декодированные кадры.
- `aosp-patches/`: патчи к проектам AOSP — какие применять и где, решает
  `series.json`, а не номера файлов.
- `launcher/`: собственный домашний экран MovieLauncher (Kotlin, Gradle).
- `installer/`: установщик в eMMC и его тесты; `rescue/`: среда восстановления на SD.
- `build/`: подготовка и сборка ядра, сборка Mesa/Panfrost, загрузка firmware,
  упаковка boot.img, проверка замыкания библиотек vendor.
- `tools/dectest/`, `tools/vp9cap/`, `tools/h96test/`, `tools/boot-audit/`,
  `tests/`: воспроизведение, сравнение кадров, регрессии, разбор загрузочных образов.

Комментарии в исходниках местами ссылаются на файлы `docs/…` — это закрытый
инженерный журнал сопровождающего, в этот репозиторий он не входит; «ТЗ §N» и
«Milestone N» — пункты его закрытого технического задания и плана работ.
Выводы, которые остаются в силе, перенесены в HISTORY.md и STATUS.md.

Полный тракт видео: приложение → MediaCodec/Codec2 → V4L2 OUTPUT →
meson-vdec/firmware → V4L2 CAPTURE → MMAP-копия/Android-буфер →
composer/DRM → HDMI. Ищите первую стадию, на которой результат неверен.

## Сборка ядра (проверено)

```bash
sudo apt install build-essential gcc-aarch64-linux-gnu bc flex bison libssl-dev libelf-dev \
                 device-tree-compiler python3 git
git clone --depth 1 --branch v7.1 \
    https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git linux
build/prepare-kernel.sh linux          # отказ, если база не 8cd9520d35a6 или дерево грязное
build/build-kernel.sh linux kout       # kout — новый, ещё не существующий каталог
```

`prepare-kernel.sh` применяет активный ряд по шагам и коммитит каждый шаг,
`build-kernel.sh` собирает `Image`, `Image.gz` и DTB только в пустом каталоге:
старые объектные файлы не могут попасть в результат. Любой `make` в дереве
ядра без `ARCH=arm64` молча делает конфиг под архитектуру хоста — скрипт
проверяет это до сборки.

## Firmware, лаунчер, boot.img

```bash
sudo apt install abootimg                    # упаковщик boot.img (mkbootimg.sh, rescue/mkrescue.sh)
build/fetch-firmware.sh                      # микрокод meson-vdec и Wi-Fi QCA9377, сверка SHA-256
(cd launcher && ./gradlew assembleRelease)   # затем APK — в device/h96proplus/prebuilt-apps/
build/mkbootimg.sh --kernel kout/arch/arm64/boot/Image.gz \
    --ramdisk $AOSP_ROOT/out/target/product/h96proplus/ramdisk.img \
    --board installer/boards/h96proplus-czs32v3.json --out boot.img
```

Лаунчеру нужны JDK (не JRE) и Android SDK с платформой 35; окружение и
копирование `app-release-unsigned.apk` под именем `MovieLauncher.apk` — в
[launcher/README.md](launcher/README.md#сборка). Собирайте на ext4, не на `/mnt/c`.

`mkbootimg.sh` берёт разметку для `blkdevparts` из описания платы установщика,
чтобы ядро и установщик видели одни и те же разделы.

## AOSP (полная сборка проверена 15.10.2026)

База: `https://android.googlesource.com/platform/manifest`, тег
`android-15.0.0_r36` (коммит манифеста `a0601d2912a6cedcaf97e1372173f8704a2715b0`,
`BP1A.250505.005.D1`). Продукт `h96proplus`, цель `h96proplus-trunk_staging-userdebug`.

```bash
repo init -u https://android.googlesource.com/platform/manifest -b android-15.0.0_r36
repo sync -c -j8
```

1. `build/fetch-firmware.sh`, затем `device/h96proplus` → `$AOSP_ROOT/device/h96proplus`
   и `kernel/firmware` → `$AOSP_ROOT/kernel/firmware` (оттуда `device.mk` берёт
   Wi-Fi firmware); файлы `aosp-overlay/…` поверх одноимённых путей AOSP
   (для `external/v4l2_codec2` — модуль целиком).
2. Патчи со статусом `active` из `aosp-patches/series.json`, каждый в своём
   каталоге `apply_in`, сначала `git apply --check`. Патч 0012 не применять.
3. Mesa/Panfrost: `sudo apt install meson ninja-build pkg-config bison flex python3-mako python3-yaml`,
   NDK r27c (`android-ndk-r27c-linux.zip` с dl.google.com), затем
   `AOSP_ROOT=… NDK=…/android-ndk-r27c OUT=… build/build-mesa.sh`
   и `$OUT/lib64/*.so` → `device/h96proplus/mesa/lib64/`.
4. `source build/envsetup.sh` (не под `set -u`), `lunch h96proplus-trunk_staging-userdebug`
   (не через конвейер), `m`. На машинах с небольшой памятью — `SOONG_GOMEMLIMIT`
   вместе с патчем 0003.
5. `boot.img` — `build/mkbootimg.sh` из ядра `build-kernel.sh` и `ramdisk.img`
   этой сборки (раздел «Firmware, лаунчер, boot.img»). DTB в boot.img не входит —
   см. [dt/README.md](dt/README.md).

Если образы будут кому-то передаваться, ещё до первой сборки задайте
нейтральные `export BUILD_HOSTNAME=builder BUILD_USERNAME=h96` (или свои): иначе
имя вашей машины и пользователя попадут в `ro.build.host`/`ro.build.user`
системного `build.prop`. Смена `BUILD_USERNAME` между сборками заново
запускает анализ soong.

Сборка с публичными test-keys AOSP — сборка разработчика, а не защищённый выпуск.

### Проверенная сборка (15.10.2026)

Описание выше прогнано целиком из свежего клона этого репозитория на новом
дереве r36 (`repo init --depth=1`), на отдельном диске и без доступа к дереву
сопровождающего. Хост: WSL2 с Ubuntu 24.04, 4 ядра без SMT, 18 ГБ памяти и
32 ГБ подкачки, `m -j3`, `SOONG_GOMEMLIMIT=14GiB`.

- **Время.** Чистая сборка — около 20 часов (172 822 задачи ninja), из них
  анализ soong — около часа. Пересборка после правки `device.mk` — 51 минута:
  анализ повторяется, потому что список пакетов продукта входит в переменные soong.
- **Память.** Анализ soong держал около 17 ГБ и ещё несколько ГБ подкачки.
- **Диск.** 205 ГБ: исходники около 92 ГБ, `.repo` 29 ГБ, `out/` 84 ГБ; без
  `--depth=1` каталог `.repo` заметно больше.
- **Образы.** `system.img` 830 МБ и `vendor.img` 82 МБ (sparse), `ramdisk.img`
  1,8 МБ, `boot.img` 21,6 МБ — все помещаются в свои разделы. Побайтной
  воспроизводимости не ждите: в образах метки времени и номер сборки.
- **Состав.** Шесть библиотек Mesa в `vendor/lib64/egl` и `vendor/lib64`,
  побайтно равные выходу `build-mesa.sh`; микрокод meson-vdec и Wi-Fi QCA9377
  со сверенными хэшами; `MovieLauncher` в `system/app`, Launcher3 и пакетов
  Google нет; Codec2 (`android.hardware.media.c2@1.2-service-v4l2-64`), gralloc
  minigbm, APEX drm_hwcomposer, `h96mouse`; `ro.adb.secure=1`, ADB на TCP 5555,
  SELinux permissive (из командной строки ядра).
- **Библиотеки.** `build/vendor-lib-closure.sh` находит полное замыкание у всех
  28 ELF-файлов в `vendor/bin`, `vendor/lib64/egl` и `vendor/lib64/hw`.

Прогон нашёл и исправил в этом репозитории пять ошибок: скрипты без бита
исполнения; импорт MovieLauncher без способа подписи (soong останавливался);
библиотеки Mesa, объявленные, но не устанавливаемые в продукт; драйвер
`libgallium_dri.so` в подкаталоге `dri`, где загрузчик EGL его не ищет;
неверный список LLNDK в `vendor-lib-closure.sh`. Обе ошибки с Mesa у
сопровождающего скрывала пересадка файлов в готовые образы.

**На приставке образы этой сборки не загружались** — сборка подтверждает
рецепт, но не работу системы.

В WSL2 учтите: когда закрывается последний сеанс `wsl.exe`, WSL выключает весь
дистрибутив — вместе со службами systemd и фоновыми процессами. На время
сборки держите открытым хотя бы один сеанс.

## Что должен содержать полностью воспроизводимый рецепт

1. Зафиксированные upstream URL и полные commit SHA для AOSP, Linux, Mesa,
   DRM/composer и Codec2; XML-манифест AOSP с ревизиями.
2. Упорядоченный ряд патчей для каждого дерева с базой, зависимостями, статусом
   active/superseded/experiment и тестом (для ядра и AOSP это `series.json`).
3. Фактические config, DTB, toolchain, build-флаги и версии упаковщиков.
4. Firmware и сторонние компоненты из проверяемых источников с хэшами и
   лицензиями ([LICENSES.md](LICENSES.md)). Путь к файлу на чужой машине не источник.
5. Сборку boot/ramdisk/system/vendor из чистых входов без чтения данных рабочей
   приставки, с метками SELinux и полным набором библиотек
   (`build/vendor-lib-closure.sh`).
6. Сборку в новом каталоге вывода и проверку содержимого результата.
7. Паспорт выпуска ([release-manifest.json](release-manifest.json)): исходники,
   патчи, команды, версии, размеры и SHA-256, загружаемый DTB, тесты и откат.

Побайтная воспроизводимость — отдельный критерий; меняющиеся timestamp и ключи
нельзя молча игнорировать.

## Консоль UART

На верхней стороне платы, справа от модуля Wi-Fi, три контакта с маркировкой
`G` `T` `R` (земля, TX SoC, RX SoC). Только адаптер с логикой **3,3 В**,
линию VCC адаптера не подключать; `T` платы — на RX адаптера, `R` — на TX.
Порт: 115200 8N1 без управления потоком. Перед подключением проверьте
мультиметром, что `G` — действительно земля. Консоль нужна, когда ядро падает
раньше, чем поднимается HDMI.

## Проверки перед выпуском

Сначала offline-проверки состава и установщика, затем одна согласованная
серия на заявленной плате. Не стирайте данные владельца ради чистого состояния:
нужен отдельный носитель/устройство или согласованное окно очистки с
проверенным восстановлением.

Проверяйте начало и конец видео, перемотку в обе стороны и за пределы кэша,
смену роликов, длительный просмотр, H.264/VP9/HEVC и аппаратный компонент.
Для корректности сравнивайте Y/U/V с эталоном на законно распространяемом
локальном клипе; сетевой ролик полезен как дополнительная проверка приложения.
Полное хэширование может менять темп работы и скрывать гонку — фиксируйте
его влияние.

Для сна проверяйте реальный пульт, IRQ-счётчики, смену Ethernet-link, USB,
звук и изображение. Отсутствие подходящей строки в узком grep не означает
PASS. Ошибка или отсутствующее измерение должно давать FAIL/NOT TESTED.

Для интерфейса проверяйте вход в Settings и Wi-Fi без мыши, клавиатуру,
масштаб всего экрана с совпадающим указателем, отмену изменения и reboot.
Загрузку без HDMI и подключение телевизора после старта отмечайте отдельно.

## Работа над конкретным дефектом

Запишите воспроизведение и исходную конфигурацию, выберите проверку,
различающую ближайшие гипотезы, внесите ограниченное изменение и сравните
с исходным состоянием. Не повышайте приоритет гипотезы только потому,
что она часто повторялась в старых отчётах.

В PR укажите проблему, изменение поведения, источник доказательств, границы
проверки и откат. Не размещайте в PR токены, подписанные URL, полные личные
журналы, а также профиль, план и бэкап установщика — они идентифицируют вашу
приставку.
