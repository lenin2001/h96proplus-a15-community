# 0027 - why this shape (synthesis of 3 designs + 3 adversarial reviews)

Implement the shared core of designs A and C — "park the parsed frame, re-issue it from vdec_vb2_buf_queue()" — with three corrections that the adversarial reviews forced, and drop every esparser/watchdog hunk from designs B and C.

WHAT I VERIFIED IN THE TREE (all line numbers are real, read today):
- The diagnosis is correct. codec_vp9.c:1452-1454 returns on NULL cur_frame and never reaches amvdec_write_dos(core, VP9_DEC_STATUS_REG, VP9_10B_DECODE_SLICE) at codec_vp9.c:1492. The firmware is parked at VP9_HEAD_PARSER_DONE, raises no further mailbox IRQ, nothing re-issues it. That is exactly the frozen interrupt counter. The tree's own 04.09 comment at codec_vp9.c:2312-2320 already says "process_frame tiho vyhodit -> dekoder zavisaet".
- The unbounded park is proven safe by existing shipping behaviour: the ISR's src_change branch (codec_vp9.c:2358-2371) returns without DECODE_SLICE, and codec_vp9_resume() (codec_vp9.c:1524-1541) completes the same handshake hundreds of ms later. Same firmware state, same restart primitive.

CORRECTION 1 (from review A, and it is real — I confirmed it). The retry MUST refresh the ANC2AXI reference table. codec_hevc_setup_buffers_gxl() (codec_hevc_common.c:122-186) writes the table by index and, for an index whose vb is not yet mapped (vb2_plane_cookie()==NULL), writes carry-forward last_y/last_uv — another buffer's address. codec_vp9_ops (codec_vp9.c:2388-2397) has NO .program_capture_buf, so VP9 has no fix-up path; only H264 does (codec_h264.c:492-496, amvdec_reprogram_canvas_slot). A late-arriving buffer would decode correctly (set_sao gives the real write address) but be read back as a reference from a stale address — the "four vertical bands" class, documented in the tree's own 05.09 "Variant B" comment. Without this correction the patch trades a dead decoder for a corrupt picture.
  BUT review A's proposed remedy (call codec_hevc_setup_buffers()) is wrong from a QBUF hot path: on 10-bit it enters codec_hevc_alloc_fbc_buffers() (codec_hevc_common.c:259-289), which overwrites comm->fbc_buffer_vaddr[] WITHOUT freeing — a full FBC-set leak per call. So I add a tiny no-allocation wrapper, codec_hevc_refresh_buffers(), that does only the table rewrite. On GXM 8-bit NV12M it is pure MMIO (use_mmu/use_fbc/use_downsample all 0).

CORRECTION 2 (reviews A and C disagreed; C is right, but A's cost objection is also right). Park on BOTH NULL exits of get_new_frame — the empty-queue exit (codec_vp9.c:1350) AND the tries-exhausted exit (codec_vp9.c:1371, the 01.09 fix). The second is the MORE common steady-state failure: the loop rotates without shortening the queue, so the inner NULL at :1381 only fires when the queue held exactly one entry; with >=2 entries all held as references you land at :1371. Parking only on the first exit, as review A demanded, leaves the frequent case fatal. A's cost objection is answered not by refusing to park but by a pre-check in the hook: if the returned index is still a live VP9 reference (codec_vp9_get_frame_by_idx), it cannot break the tie — while parked no decoding happens, so ref_frame_map is frozen — and we return without entering get_new_frame. That kills the per-QBUF queue rotation and the dev_err flood A feared, at the cost of one bounded list walk (<=24 entries).

CORRECTION 3 (from review B, and it is right). Do NOT add design B's `&& !vp9->frame_pending` guard on codec_vp9_rm_noshow_frame(). I read codec_vp9_rm_noshow_frame (codec_vp9.c:1410-1440): it already skips cur_frame, prev_frame and anything codec_vp9_is_ref() — that check IS the 01.09 fix. A second call can only release a genuinely dead noshow frame, which HELPS the retry. B's guard would remove the retry path's only source of returned buffers. Design B's claimed re-entrancy regression (set_mc/set_sao/fill_mmu_map re-run) also never happens: the park returns at :1453, before all of them.

WHAT I REJECT OUTRIGHT:
- esparser.c u32 underflow hunk (designs B and C). The defect is REAL and I confirmed it (esparser.c:299 `u32 num_dst_bufs`, :317 `-= 3`, :320 comparison) — but it is not on the failing path. The reproduced freeze goes ISR src_change -> amvdec_src_change (vdec_helpers.c:672) -> resume -> process_frame -> get_new_frame, with no AU queued and no throttle evaluated. Worse, both proposed repairs stall input: signed arithmetic gives `queued >= pending + ready - 3` with an RHS <= 0 in exactly the post-switch window, and C's saturating form gives `queued >= 0`, unconditionally true. esparser_queued_bufs only decrements in amvdec_dst_buf_done/_offset (vdec_helpers.c:559/609) and never for the noshow requeues at codec_vp9.c:684/1434/2333, so it drifts upward forever. With no VP9 watchdog that is a silent permanent input stop. Keep this as a separate, separately-A/B'd patch.
- 0025 watchdog hunk (design B). vdec_codec_needs_recycle() (vdec.c:47-52) needs can_recycle+recycle; only codec_h264.c:504-505 and codec_mpeg12.c have them. vdec.c:562 never spawns the recycle thread for VP9, so the entire 0025 stall/abort at vdec.c:120-155 is absent from the failing path. The hunk is inert for VP9 and would weaken H264's only automatic hang recovery.
- Raising dpb_size / min_buffers / adding scratch buffers (design B's own conclusion, which I agree with). Note for the record: GXM VP9 max_buffers really is 22 (vdec_platform.c:171, with the 03.09 CCodec-limit comment) — review B called that number invented; it is in the tree.
- HEVC (codec_hevc.c:794) is deliberately left alone: same drop, but it needs its own on-hardware A/B, and codec_hevc_resume() does NOT take hevc->lock while amvdec_src_change() IS called under it (codec_hevc.c ISR) — copying this scheme blindly to HEVC would self-deadlock.

ONE FACTUAL CORRECTION TO REVIEW A, which its verdict leaned on: its claim that the deadlock analysis "identifies the wrong lock throughout" is itself wrong. I traced it: VIDIOC_QBUF/STREAMON/STREAMOFF carry INFO_FL_QUEUE (v4l2-ioctl.c:2926/2929/2930), and v4l2_ioctl_get_lock() (v4l2-ioctl.c:3010-3025) returns vfh->m2m_ctx->q_lock, which v4l2-mem2mem.c:1271 sets to out_q_ctx->q.lock == &sess->lock (vdec.c:1116). vdev->lock = &core->lock (vdec.c:1394) is only the fallback. So vdec_vb2_buf_queue, vdec_start_streaming and vdec_stop_streaming DO all run under sess->lock, exactly as designs A and C stated, and kfree(sess->priv) (vdec.c:675) is serialised against the new hook by construction.
